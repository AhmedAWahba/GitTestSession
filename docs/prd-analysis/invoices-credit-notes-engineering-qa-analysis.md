# Invoices and Credit Notes: Engineering QA Analysis

**Review date:** 2026-10-15  
**Review role:** Senior QA / static requirements and prototype analysis  
**Implementation baseline:** `Billing PRD (Engineering)` embedded in the Master APEX PRD Set  
**Prototype:** https://apex-web-app-prototype.vercel.app/home

## 1. Executive Assessment

The Engineering Billing PRD defines a coherent initial-release product: import already-cleared XML invoices, credit notes and debit notes; validate each file/document independently; preserve accepted source facts; support repair and explicit resume for actionable records; and keep records private to the current Business. CSV, system connections, document authoring, collection, financing and ledger effects are not part of this Billing release.

The prototype demonstrates a substantial set of list, detail, upload, import-result and role examples. However, the inspected preview is not aligned with the Engineering baseline in several release-critical areas.

> [!WARNING]
> **Confirmed TRD/design differences:** The prototype rejects debit notes although Engineering includes them; splits Invoices and Credit Notes instead of one combined list; treats missing partners/referenced invoices as terminal Rejected outcomes instead of Action required plus repair and Resume; omits the complete result-count/`Processing finished` contract and uses `Added`; and the inspected rejected-import detail has no original-file download control. See the evidence-by-requirement table in [Section 5](#5-prototype-comparison-engineering-trd-vs-observed-ui).

> [!IMPORTANT]
> **Questions needing decisions:** Exact upload and recovery limits, retention/legal-hold and support policy, performance targets, duplicate-compatibility rules, note amount validation, and source-issue versus document-rejection classification remain open. See the prioritized question list in [Section 4](#4-prioritized-questions-for-missing-or-ambiguous-behavior).

These are a mix of confirmed prototype mismatches and requirements still needing decisions; the detailed analysis below keeps those categories separate.

## 2. Source Authority and Review Boundaries

The user-designated source of truth is the `Billing PRD (Engineering)` section at [Master APEX PRD Set.md](../Master%20APEX%20PRD%20Set.md#L4928). This analysis treats that section and its data, non-functional, dependency and outstanding-detail sections as the implementation baseline.

The earlier `APEX Invoices and Credit Notes` product section in the same master file conflicts with the Engineering baseline: it excludes debit notes, while Engineering includes debit notes in the initial release. The older [invoice analysis.md](../invoice%20analysis.md#L20) discusses invoice authoring, ZATCA submission, CSV/API channels and balance changes that are explicitly outside this Engineering release. Those older artifacts are not used as implementation acceptance criteria here. Product/Engineering should formally mark their supersession to prevent competing test expectations.

The existing [invoice-credit-notes-senior-qc-review.md](invoice-credit-notes-senior-qc-review.md) is useful historical input, but some statements are stale or conflict with Engineering. In particular, the current Engineering PRD permits a note to reference several invoices; the previous review's one-invoice premise must not be carried forward. A cap against outstanding balance is also not an appropriate assumption: Engineering says accepted notes do not change invoice amounts or create balances. Whether a note's stated amount is checked against the combined referenced invoice totals remains an open question below.

The prototype was inspected interactively using its seeded preview/demo states. This is a UI/design assessment only. No real XML was submitted, no API behavior or database isolation was tested, and demo-case labels are not evidence of server-side enforcement. Findings below distinguish directly observed screens from catalogued demo behavior and unverified controls.

[BIL-02](../Master%20APEX%20PRD%20Set.md#L5036) | This is a top-level information architecture contract, not merely a filter implementation. A new document requires the current Business's active partner relationship. Business/party identification problems reject; a missing/inactive relationship is repairable Action required. [BIL-11](../Master%20APEX%20PRD%20Set.md#L5208) | Keep identity-resolution failures distinct from relationship failures. Test each supported identifier, conflicting identifiers resolving to different businesses, missing identifiers, same-party documents, reciprocal-only relationships, and role-specific repair/resume. |
| Detect duplicates | Validate the incoming document fully before duplicate comparison. Seller + document number identify a candidate within current Business records; type/year do not form separate number ranges. Trim only outer whitespace; preserve case, punctuation, internal whitespace and leading zeroes. Compatible repeat links to existing record and adds the new original file without changing accepted facts; conflicting recognized facts reject. Concurrent repeats create at most one new record. [BIL-07](../Master%20APEX%20PRD%20Set.md#L5123) | Requires a canonical comparison matrix for optional fields, hashes, source identifiers and differences among accepted invoice/credit/debit-note types. Links are accepted all-or-nothing. [BIL-09](../Master%20APEX%20PRD%20Set.md#L5172) | Test one and many references, duplicated reference, missing reference, mixed missing and contradictory references, same-day date, party mismatch, link atomicity, note visibility from every referenced invoice, and full stated amount on each reverse link. |
| Repair a missing referenced invoice | Allow a short wait for recently imported invoices, then show Action required listing every missing number. APEX/system lookup delay stays Processing. Include payment-request reference if present without promising collection changes. ## 4. Prioritized Questions for Missing or Ambiguous Behavior

Questions below avoid re-asking behavior already explicitly answered by Engineering. Decisions should be recorded against the Engineering baseline and reflected in acceptance tests.

### P0 - Release blockers

1. **Specification authority:** Is the Engineering Billing PRD formally superseding the earlier Invoices/Credit Notes section, including its debit-note exclusion and channel assumptions? Where is the version/status decision recorded so downstream QA does not test both contracts?
2. **Upload limits:** What are the maximum file count, per-file bytes, aggregate bytes, parser/XML complexity and any per-user/business rate limits? Are the prototype's 50 files and 1 MB limits approved? What exact user-facing error applies at each boundary?
3. **Transfer recovery:** What is the recovery deadline and how is it measured? At deadline, does an expired transfer count as a terminal file outcome for `Processing finished` in every case? Can a partially received file be resumed from a byte offset, or must it restart under a new transfer correlated to the old one?
4. **Retention and access:** What retention periods, legal holds, backup/deletion rules and support access controls apply to accepted records, original files, rejected attempts, transfer metadata and audit data? What happens when retention expires?
5. **Support route:** Which support channel is approved before release? How does it provide acknowledgement, a reference/follow-up path, safe handling of original files and an auditable investigation? Is the prototype's `support@qawafel.sa` address the approved route?
6. **Performance/operations:** What workload, processing completion target, oldest-queued threshold and support-intervention target constitute acceptable service? When does automatic recovery stop and an operator need to act?

### P1 - Data integrity and state model

7. **Amount comparisons for notes:** Are note amounts validated against the sum of the referenced invoice amounts, or are links and dates the only cross-document checks? Clarify that no cap is based on current outstanding/payment state, which is not modeled by Billing.
8. **Duplicate compatibility:** Which recognized fields are compared, and what are the exact outcomes for absent-vs-present optional values, multiple supplied files, differing document hashes, QR/signature summaries and repeated source identifiers? Which hash conflicts are identity conflicts versus compatibility differences?
9. **Duplicate key across types:** Engineering says seller + number identify the candidate and type/year do not create separate ranges, while also requiring a conflicting type to reject. Confirm exact outcomes for invoice vs credit note vs debit note with same seller/number, and for that identity in sales and purchase perspectives of the same Business.
10. **Date/time boundary:** The rule rejects an issue date after the Saudi date retained when processing starts. Does a future issue time on the same Saudi calendar date pass? How are malformed time/offset values, daylight/date-boundary input, and resumed documents treated?
11. **Precision/rounding contract:** Which exact decimal scales and rounding mode apply to quantities, unit prices, tax rates, tax amounts, adjustments and totals for each supported XML field? How are negative payable rounding and zero/negative edge values handled? The worked example is useful but not a complete precision table.
12. **Party resolution precedence:** If several valid seller/buyer identifiers are present, what is the complete rule when one does not resolve, when identifiers resolve to different Businesses, or when a group tax identifier is the only match? What field-level reason is exposed without leaking another Business's identity?
13. **Source issue vs document rejection:** Define a complete outcome matrix for unreadable XML, unsupported XML version/profile/type, no recognized document, multiple documents in one file, malformed content, and a recognized document with invalid values. Which conditions are file-level source issues versus document-level Rejected?
14. **Failure reason contract:** Is a stable machine-readable reason code required for support, analytics or future exports? The initial release only commits to readable on-screen reasons; confirm localization and code evolution expectations.

### P2 - UX, navigation and future compatibility

15. **Search/filter semantics:** What matching semantics apply to document-number search (partial/exact, case, outer whitespace, Arabic/English numerals)? Are date-range endpoints inclusive and in Saudi time? What stable ordering and pagination size should QA assert?
16. **Import scope confirmation:** Should importing debit notes be exposed in the same UI and supported with the same explicit prior-clearance statement as invoices/credit notes? Confirm the exact UI copy when a document type is recognized but outside a future release's enabled scope.
17. **Support report payload:** Which fields are mandatory in the report and how is the original-file association supplied without an open file link? What does the user see if the route is temporarily unavailable?
18. **Localization/accessibility:** Which languages are in the initial release? Confirm Arabic RTL coverage for the full import/result/detail flow, including validation reasons, numeric formatting, progress state and accessible result announcements.
19. **Cross-feature effects:** The prototype home page shows receivables/collection/financing concepts, while Engineering excludes balances and collection from Billing. Which separate domain owns those widgets, and how will QA ensure importing/accepting a note cannot mutate those values or imply a balance?
20. **Future CSV:** Before BIL-17 ships, who approves its exact schema, missing-vs-zero semantics, row grouping, limits, calculations and parity with XML? Until then, confirm that CSV/PDF/API options remain absent from initial-release surfaces.

## 6. Recommended QA Test Pack

1. **Business access/isolation:** Owner, Admin and Member; promotion/demotion while pages remain open; access removal; direct list/detail/result/file URLs across two fixture Businesses; identical not-found response; verify counts/search/links do not leak.
2. **List behavior:** combined type/perspective/partner/date filters; empty vs no match; search normalization; stable sort and pagination; return from detail restores filters; verify a single list includes all three types.
3. **Upload validation:** accepted XML per type; many files; one over every limit; extension/media-type spoof; malformed/unrecognized XML; multiple documents in one file; declaration required; unsupported type/currency/profile/status; no API call can bypass limits.
4. **Transfer lifecycle:** lost initiation response, repeated initiation, interrupted upload, recover before/at/after deadline, cancel one of several, terminal transfer, new attempt correlation, navigation/reconnect and completed transfer awaiting interpretation.
5. **Document validation:** required seller/buyer identifiers and addresses; identifier mismatch; each supported VAT treatment/reason; line/adjustment/prepayment totals; QR/hash/signature consistency checks as specified; all validation messages stable and safe; no partial registration.
6. **Outcome aggregation:** all five document results plus file source issues; counts include zeroes; no overall percentage; terminal files; `Processing finished` timing; mixed accepted/rejected siblings; delay keeps Processing and does not request user repair.
7. **Duplicates:** compatible repeat, optional-value cases, new original file linked, conflicts by type/party/date/amount/hash, leading zero/case/punctuation/outer-space boundaries, same seller across years, different sellers, concurrent identical requests, invalid file with a matching number.
8. **Notes and repair:** one/many invoice links, repeated link, missing and delayed references, party mismatch, note-before-invoice date, same-day, mixed missing plus known contradiction, atomic links, Action required then explicit Resume, inactive/missing Business Partner repair, stale page and repeated Resume.
9. **Records/files/support:** source facts survive profile changes; no inferred balances; invoice-note navigation in both directions; accepted/duplicate/rejected/action-required downloads; file attachment safety; expired download access; capture-report acknowledgement/reference/audit; immutable accepted facts.
10. **Non-functional gates:** server limit and tenant-isolation tests, process restart/repeated delivery, privacy-safe logs, keyboard-only navigation, screen-reader result announcements, Arabic RTL and number formatting, agreed performance workload, retention/legal hold and support-access evidence.

## 7. Release Readiness Recommendation

Do not use the current prototype as the sole acceptance oracle. Resolve the source-precedence decision and the P0 questions first. Before implementation sign-off, reconcile the debit-note scope, combined list, Action required/Resume paths, complete result summary, rejected-file download and approved limits/support route. Then map each BIL requirement and non-functional gate to executable tests; prototype screenshots or demo labels alone do not prove service-side enforcement.
