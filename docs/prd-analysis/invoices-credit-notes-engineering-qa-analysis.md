# Invoices and Credit Notes: Engineering QA Analysis

**Review date:** 2026-10-15  
**Review role:** Senior QA / static requirements and prototype analysis  
**Implementation baseline:** `Billing PRD (Engineering)` embedded in the Master APEX PRD Set  
**Prototype:** https://apex-web-app-prototype.vercel.app/home

## 1. Executive Assessment

The Engineering Billing PRD defines a coherent initial-release product: import already-cleared XML invoices, credit notes and debit notes; validate each file/document independently; preserve accepted source facts; support repair and explicit resume for actionable records; and keep records private to the current Business. CSV, system connections, document authoring, collection, financing and ledger effects are not part of this Billing release.

The prototype demonstrates a substantial set of list, detail, upload, import-result and role examples. However, the inspected preview is not aligned with the Engineering baseline in several release-critical areas.

> [!WARNING]
> **Confirmed TRD/design differences:** The prototype rejects debit notes although Engineering includes them; splits Invoices and Credit Notes instead of one combined list; treats missing partners/referenced invoices as terminal Rejected outcomes instead of Action required plus repair and Resume; omits the complete result-count/`Processing finished` contract and uses `Added`; and the inspected rejected-import detail has no original-file download control. See the evidence-by-requirement table in [Section 5](#5-prototype-comparison-engineering-trd-vs-observed-ui).

> [!IMPORTANT]
> **Questions still open:** Approved XML/parser limits, numeric precision, credit-note reason/value validation, earliest allowed issue dates, due-date ordering, imported-item/catalog behavior, upload recovery deadlines, retention/support policy, processing targets, source-versus-document classification, and search/accessibility edge rules. The verified, status-tracked backlog is in [Section 4](#4-prioritized-questions-after-reconciliation).

These are a mix of confirmed prototype mismatches and requirements still needing decisions; the detailed analysis below keeps those categories separate.

## 2. Source Authority and Review Boundaries

The user-designated source of truth is the `Billing PRD (Engineering)` section at [Master APEX PRD Set.md](../Master%20APEX%20PRD%20Set.md#L4928). This analysis treats that section and its data, non-functional, dependency and outstanding-detail sections as the implementation baseline.

The earlier `APEX Invoices and Credit Notes` product section in the same master file conflicts with the Engineering baseline: it excludes debit notes, while Engineering includes debit notes in the initial release. The older [invoice analysis.md](../invoice%20analysis.md#L20) discusses invoice authoring, ZATCA submission, CSV/API channels and balance changes that are explicitly outside this Engineering release. Those older artifacts are not used as implementation acceptance criteria here. Product/Engineering should formally mark their supersession to prevent competing test expectations.

The existing [invoice-credit-notes-senior-qc-review.md](invoice-credit-notes-senior-qc-review.md) is useful historical input, but some statements are stale or conflict with Engineering. In particular, the current Engineering PRD permits a note to reference several invoices; the previous review's one-invoice premise must not be carried forward. A cap against outstanding balance is also not an appropriate assumption: Engineering says accepted notes do not change invoice amounts or create balances. Whether a note's stated amount is checked against the combined referenced invoice totals remains an open question below.

The prototype was inspected interactively using its seeded preview/demo states. This is a UI/design assessment only. No real XML was submitted, no API behavior or database isolation was tested, and demo-case labels are not evidence of server-side enforcement. Findings below distinguish directly observed screens from catalogued demo behavior and unverified controls.

## 3. Engineering Flow Analysis

| Flow | Engineering requirement / expected QA result | QA analysis and risk |
|---|---|---|
| Business context and access | All work is scoped to the currently selected Business. Owner/Admin can import, recover/cancel uploads and resume; Member can view records/results and download files but cannot import or resume. Role changes and access removal apply to subsequent requests, including from an already-open page. [BIL-01](../Master%20APEX%20PRD%20Set.md#L5019) | Test current-Business scoping across list/search/counts/details/links/files/results and direct requests. | Find records | One list contains accepted invoices, credit notes and debit notes across sales/purchase perspectives. [BIL-02](../Master%20APEX%20PRD%20Set.md#L5036) | This is a top-level information architecture contract, not merely a filter implementation. A split invoice/CN destination changes discoverability and complicates combined filtering and linked-note navigation. |
| Start an import | Owner/Admin selects one or more files within published, server-enforced limits, sees supported types and prior-clearance declaration, then explicitly submits. Initial release is standard B2B Saudi-riyal XML for invoice, credit note or debit note; each file has at most one document. No CSV, scan/PDF or connector is offered yet. File extension/media type cannot establish document validity. |
| Recover/cancel transfer | Transfer state is distinct from document interpretation. Lost initiation/upload responses can recover existing handles; eligible pending transfers may be resumed before a fixed deadline; terminal transfers cannot reopen; canceling one transfer cannot undo siblings or accepted documents. [BIL-04](../Master%20APEX%20PRD%20Set.md#L5069) | Needs boundary tests around retry races, expired transfers, cancellation timing, repeated initiation and a completed transfer still awaiting interpretation. Recovery deadline/value is unresolved. |
| Process and report results | Each identified document gets exactly one Processing, Action required, Accepted, Rejected or Duplicate result. File-level source issues stay distinct from document rejection. Siblings are independent. [BIL-05](../Master%20APEX%20PRD%20Set.md#L5085) | Test mixed-validity batches, files with no identifiable document, transfer terminal states, processing delay, leave/return, ordering, refresh/lost notifications and state/count consistency. | Resolve parties and partner relationship | Seller and buyer must resolve to verified Businesses by supported identifiers; current Business must be one of them and cannot equal the other party. A new document requires the current Business's active partner relationship. Business/party identification problems reject; a missing/inactive relationship is repairable Action required. [BIL-11](../Master%20APEX%20PRD%20Set.md#L5208) | Keep identity-resolution failures distinct from relationship failures. Test each supported identifier, conflicting identifiers resolving to different businesses, missing identifiers, same-party documents, reciprocal-only relationships, and role-specific repair/resume. |
| Detect duplicates | Validate the incoming document fully before duplicate comparison. Seller + document number identify a candidate within current Business records; type/year do not form separate number ranges. Trim only outer whitespace; preserve case, punctuation, internal whitespace and leading zeroes. Compatible repeat links to existing record and adds the new original file without changing accepted facts; conflicting recognized facts reject. Concurrent repeats create at most one new record. [BIL-07](../Master%20APEX%20PRD%20Set.md#L5123) | Requires a canonical comparison matrix for optional fields, hashes, source identifiers and differences among accepted invoice/credit/debit-note types. Test same seller/number across types and years, distinct sellers, concurrent upload, invalid duplicate, and cross-channel behavior only if/when another channel ships. |
| Record notes and references | Credit/debit note requires one or more reasons and distinct invoice references; all referenced invoices must be accepted in the current Business with identical seller/buyer, and note date cannot precede any invoice date. Links are accepted all-or-nothing. [BIL-09](../Master%20APEX%20PRD%20Set.md#L5172) | Test one and many references, duplicated reference, missing reference, mixed missing and contradictory references, same-day date, party mismatch, link atomicity, note visibility from every referenced invoice, and full stated amount on each reverse link. |
| Repair a missing referenced invoice | Allow a short wait for recently imported invoices, then show Action required listing every missing number. APEX/system lookup delay stays Processing. Importing the missing invoice does not auto-resume; Owner/Admin explicitly resumes and the note is checked again. [BIL-10](../Master%20APEX%20PRD%20Set.md#L5189) | The prototype's re-import instruction is not equivalent: it creates a new attempt and loses the explicit resume lifecycle. Test no cross-Business disclosure in missing-reference messages and stale-page/repeated Resume behavior. |
| Inspect accepted details and links | Show source-stated names/addresses and all captured fields; distinguish claimed clearance from independent verification; do not infer payment status, outstanding balance or financing eligibility. Temporary detail delay gives an updating/refresh state. Note detail links all invoices; invoice detail lists related notes with full stated amounts. [BIL-06](../Master%20APEX%20PRD%20Set.md#L5106) [BIL-13](../Master%20APEX%20PRD%20Set.md#L5241) | Compare representative invoice, purchase invoice, sales/purchase note, multiple-reference note, optional/missing fields and prepayment example. Profile changes must not rewrite source facts. No balance/payment side effects should be attributed to import. |
| Download original files | Owner/Admin/Member can download files from accepted/duplicate details and rejected/actionable results. Downloads are attachments with safe names, do not execute inline, require current access and disclose nothing across Businesses. [BIL-12](../Master%20APEX%20PRD%20Set.md#L5225) | Test accepted, duplicate, rejected, action-required, renewed temporary access, expired links, role changes and cross-Business access. The inspected rejected-result screen had no download control. |
| Handle technical delay | Delay keeps work Processing and tells the user the submission is saved; operational recovery continues the same work without a second record. Authorized support action is audited. [BIL-14](../Master%20APEX%20PRD%20Set.md#L5257) | Separate infrastructure delay from user-repair conditions. Verify no false missing-partner/invoice instructions during a system failure; verify once-only recovery and no duplicate acceptance. SLA/targets are unresolved. |
| Keep accepted records stable and report capture errors | No accepted facts can be edited/deleted/replaced. Capture report is distinct from issuing a note; it identifies Business/document/file/disputed fields, acknowledges and supports follow-up, and preserves original result/files. Include payment-request reference if present without promising collection changes. [BIL-15](../Master%20APEX%20PRD%20Set.md#L5273) | UI shows a support email, but acknowledgement/reference, safe file context, audit trail and follow-up process are not demonstrated. The underlying route is an outstanding release dependency. |
| Non-functional and future capabilities | Enforce finite upload/parser/query limits, durable/recoverable work, privacy-safe logging, keyboard/accessibility and RTL, agreed performance measures, and production retention/support policy. CSV is a later release; `/dev` builder is internal and must not bypass normal validation. [NFRs](../Master%20APEX%20PRD%20Set.md#L5470) [BIL-17](../Master%20APEX%20PRD%20Set.md#L5311) | UI walkthrough cannot establish durability, isolation, server limits, logging hygiene, keyboard/RTL support, load behavior or retention. These need API/service tests, operational evidence and explicit sign-off. |

- Missing/inactive partner and missing referenced-invoice questions are not open requirement questions: Engineering specifies Action required plus repair and explicit Resume. They remain **prototype conflicts** in Section 5, not unanswered questions.
- CSV structured-file row/count/format questions are deferred to BIL-17, and direct system/API import is Later. They are not initial-release questions; define CSV limits when that follow-up is scheduled.

## 6. Recommended QA Test Pack

1. **Business access/isolation:** Owner, Admin and Member; promotion/demotion while pages remain open; access removal; direct list/detail/result/file URLs across two fixture Businesses; identical not-found response; verify counts/search/links do not leak.
2. **List behavior:** combined type/perspective/partner/date filters; empty vs no match; search normalization; stable sort and pagination; return from detail restores filters; verify a single list includes all three types.
3. **Upload validation:** accepted XML per type; many files; one over every limit; extension/media-type spoof; malformed/unrecognized XML; multiple documents in one file; declaration required; unsupported type/currency/profile/status; no API call can bypass limits.
4. **Transfer lifecycle:** lost initiation response, repeated initiation, interrupted upload, recover before/at/after deadline, cancel one of several, terminal transfer, new attempt correlation, navigation/reconnect and completed transfer awaiting interpretation.
5. **Document validation:** required seller/buyer identifiers and addresses; identifier mismatch; each supported VAT treatment/reason; line/adjustment/prepayment totals; QR/hash/signature consistency checks as specified; all validation messages stable and safe; no partial registration.
6. **Outcome aggregation:** all five document results plus file source issues; counts include zeroes; no overall percentage; terminal files; `Processing finished` timing; mixed accepted/rejected siblings; delay keeps Processing and does not request user repair.
7. **Duplicates:** compatible repeat, optional-value cases, new original file linked, conflicts by type/party/date/amount/hash, leading zero/case/punctuation/outer-space boundaries, same seller across years, different sellers, concurrent identical requests, invalid file with a matching number.
8. **Notes and repair:** one/many invoice links, repeated link, missing and delayed references, party mismatch, note-before-invoice date, same-day, mixed missing plus known contradiction, atomic links, Action required then explicit Resume, inactive/missing Business Partner repair, stale page and repeated Resume.
9. **Records/files/support:** source facts survive profile changes; no inferred balances; invoice-note navigation in both directions; accepted/duplicate/rejected/action-required downloads; file attachment safety; expired download access; capture-report acknowledgement/reference/audit; immutable accepted facts.
10. **Non-functional gates:** server limit and tenant-isolation tests, process restart/repeated delivery, privacy-safe logs, keyboard-only navigation, screen-reader result announcements, Arabic RTL and number formatting, agreed performance workload, retention/legal hold and support-access evidence.

## 8. Lead Demo Runbook: End-to-End Invoice and Credit-Note Cycle

**Prepared:** 2026-10-24. Allow 20-25 minutes for the main story and 10 minutes for selected edge cases. This is a proposed demo script, not a record of executed XML tests. The Engineering Billing PRD is still labelled Draft for Product review; use it as the requested baseline and explain unresolved decisions rather than inventing expected results.

### 8.1 Opening Narrative and Scope

Say: "APEX Billing records already-issued, already-cleared business documents. We import their XML, validate the document and its Business relationships, preserve the accepted facts and original files, and link credit notes to the invoices they correct. Accepted does not mean paid, independently verified, financed or posted to an accounting ledger."

- Initial inputs are standard B2B SAR XML invoices (388), credit notes (381) and debit notes (383), one document per direct XML file; several files may be submitted together.
- Do not demonstrate invoice creation, draft editing, signing, sending to ZATCA, collecting payments or refunds as part of this release. CSV is follow-up; connectors and PDF/scanned inputs are later.
- Sales/purchase is the current Business's perspective on the seller/buyer stated in the file. A seller's import does not automatically create a buyer-side record or notification.
- A credit note is issued and cleared outside APEX. Importing it records a separate commercial adjustment; it does not edit the invoice, allocate the credit across invoices, or derive an outstanding balance.

### 8.5 Edge-Case Checklist for the Lead's Questions

| Group | Case | Expected Engineering outcome |
|---|---|---|
| File vs document | Unreadable file with no identifiable supported document | File/source issue, not an invented rejected invoice; other files remain independent. |
| Supported input | Simplified document, standalone prepayment invoice, USD currency, or source positively marked draft/rejected/uncleared | Not accepted; recognized invalid documents have appropriate rejection reasons. PDF/CSV/connectors are not advertised as initial-release inputs. |
| Required facts | Missing supply date on invoice; no commercial lines; invalid quantity/net unit price; required total missing | Reject the whole document. Supply date may be absent on a credit/debit note. Positive quantity and non-negative price are required; zero price is not inherently invalid. |
| Tax | Missing zero-rated/exempt/outside-scope reason/code; inconsistent VAT groups; contradictory QR total or issue time | Reject the complete document with safe, located reasons. APEX checks repeated facts but does not independently verify signatures or clearance. |
| Arithmetic | Wrong line net, tax summary, allowance/charge total, payable or source rounding | Reject; do not drop a bad line or recalculate to hide differences. Use the PRD's component-rounding example: 10.00 minus 1.01 = 8.99, not 9.00. |
| Optional values | Missing due date vs explicit zero amount vs supplied malformed optional fact | Absence remains unavailable and distinct from zero. Malformed supplied optional data rejects instead of being discarded. |
| Prepayment | Positive deduction without complete supporting reference/tax/special-line details | Reject. Special prepayment lines do not count as commercial lines; referenced type-386 prepayment need not exist as an accepted Billing record. Negative payable is a source fact, not an automatic refund. |
| Identity | Seller/buyer unresolved; current Business neither party; seller equals buyer; conflicting resolved identifiers | Reject identification/document issue; do not auto-create a Business. Similar names or group VAT alone are insufficient. |
| Note links | Repeated invoice reference, different seller/buyer, or note date before any referenced invoice | Reject the complete note and link set. Same-day note/invoice date passes. No partially accepted links. |
| Failure precedence | One referenced invoice missing and another has a known date/party contradiction | Reject because of the conclusive contradiction; do not leave the note merely Action required for the missing reference. |
| Repeat identity | Same seller/number reused across type or year | Type/year do not create numbering ranges; conflicting type/date rejects. Different sellers may use the same number. |
| Reference precision | INV-42 vs inv-42; 42 vs 042; INV 42 vs INV42 | Distinct references; trim outer whitespace only. Preserve letter case, punctuation, internal spaces and leading zeroes. |
| Repeat optional facts | Accepted record has no due date; compatible later upload supplies one | May be Duplicate; accepted due date remains unavailable. Conflicting supplied hashes still reject. |
| Concurrency | Two compatible identical submissions; repeated Resume; stale Action required page | At most one newly accepted record; repeated clicks do not repeat work; stale page cannot resume a later actionable result the user has not seen. |
| Mixed submission | Five documents: two Accepted, one Duplicate, one Rejected, one Action required | Processing finished with all result counts, including zero Processing. Resume changes only the actionable document to Processing and removes finished until its new result arrives. |
| Permission/isolation | Member opens import; Admin demoted while form open; other-Business record/file URL | No unauthorized mutation; enforce current access per request. Cross-Business reads use the same not-found response as unknown records, without names/amounts/file metadata. |
| Record stability | Partner deactivated; party profile edited; duplicate re-upload; capture error reported | Accepted facts and links/files remain unchanged. Authorized support explains capture-error investigation and follows up; no silent replacement or automatic collection changes. |
| Usability | Search has no matches; truly empty list; accepted detail temporarily unavailable; keyboard/RTL navigation | Distinct empty states, safe updating/refresh state, labeled inputs and non-color-only results; correct layout direction for supported languages. |

### 8.7 Closing Script and Open Decisions

Say: "The cycle is import, validate, record, inspect, and link. Each Business imports its own records independently. Keep these unresolved decisions separate from pass/fail claims: approved upload/parser/line limits and recovery deadlines; complete field-precision contract; any single/cumulative credit amount cap; earliest historical dates and due-date ordering; capture-report support route/acknowledgement; production retention/holds; and measured processing targets.
